# Bounded scan readers and persisted tracking (stage 3)

This stage builds on [stage 1 directory snapshots](scan-directory-snapshots.md) and [stage 2 incremental SQL batches](incremental-scan-batches.md). Scans remain read-only for media/NFO files. No SQLite pool, WAL, durability, production configuration, provider policy, or filename/grouping semantics changed.

## Bounded ordered preparation

`internal/library/scan_readers.go` uses **two readers by default** (one/two/four are exercised through an instance-local test setting, not a new public configuration). Traversal remains file-first and ordered. Within a directory, readers stat files/sidecars and parse filename hints into distinct slots; the caller consumes slots in traversal order. Chunks fill only the remaining space in the existing **200-candidate** batch. There is no unbounded channel, goroutine-per-file launch, whole-library cache, or cross-directory snapshot queue.

The caller is the single scan writer. It commits the existing SQL-only repository batch before NFO hydration. New database IDs are therefore known before eligible movie NFO preparation starts. NFO readers check saved metadata and use the existing Kodi basename/`movie.nfo` fallback reader; the ordered caller applies prepared records. Parsed NFOs are retained in windows of **one record per reader**, not 200 records. Input reads are limited to 1 MiB plus one overflow-detection byte even if a file grows after stat. Existing size/type/symlink validation and invalid-NFO fallback remain in place.

Memory depends on the largest directory listing/sidecar-name snapshot, pending child paths, up to 200 prepared stat candidates and their attributed sidecars, and at most two parsed NFO records by default (four in the largest test setting). XML/domain objects can occupy more memory than their bounded input; this is not a fixed-byte cap for directory width or unusually numerous sidecars. Workers join before a chunk returns, including cancellation/error, so slow reads backpressure the next chunk. No writer transaction encloses filesystem I/O or parsing.

`PrepareExistingNFO` / `HydratePreparedNFO` split metadata preparation from persistence; `HydrateExistingNFO` remains a compatibility wrapper. The repository's hydration upsert is **atomically conditional on an empty saved title**. A manual/scraped save between preparation and apply, or racing the SQL mutation, wins regardless of execution order. Ordinary Save remains unconditional. Skipped hydration emits no success log. Provider/locks are preserved together with the saved record.

Sample/Extras exclusion (including historical parent identity), movie year/TV title hints, root-layout last-hint correction across batches, and rename fingerprint invalidation are unchanged. Missing reconciliation and completed-scan time still run only after successful traversal, preparation, final flush and context checks. Cancellation/errors retain earlier committed batches without declaring unseen files missing. Persisted interrupted/retry jobs perform a fresh traversal, not an in-memory resume.

## Persisted frontend tracking

`useLibrary` now submits a persisted job and returns after queue acknowledgement/status refresh, rather than keeping a 120 × 500 ms polling loop per submission. One scheduler per mounted library:

- refreshes at two-second intervals while scans are tracked or active pages remain, and ten seconds while idle;
- serializes/deduplicates overlapping refresh calls; schedules the next cycle only after the current cycle finishes;
- backs off request errors from two seconds to at most 30 seconds, with a 15-second abort deadline for job snapshot requests;
- discovers active scans on mount/reload/navigation, independently of the latest-100 history limit;
- fetches at most one active page, one recent page and eight sequential exact job lookups per cycle, rotating exact lookups across older tracked jobs;
- refreshes the current movie/TV queries and sources, and notifies the selected inspector once on observed `succeeded`, `failed`, `cancelled` or `interrupted` transitions;
- never treats an absent history row or failed request as success; shows errors and retries;
- cancels timers/requests and ignores late job responses after scope disposal. A queued server job continues independently of the page.

Active jobs are discovered through `GET /api/v1/jobs?activeScans=true&after=<id>`, a fixed maximum 100-row ascending-ID keyset page with `nextCursor` (zero when exhausted). `GET /api/v1/jobs/{id}` retrieves an exact persisted job, including a terminal scan older than recent history. Both require a session and exclude private payloads. Default `GET /api/v1/jobs` remains latest 100, unchanged. Discovery across more than 100 active scans takes multiple cycles; exact-terminal processing for many old scans is deliberately rate-bounded. Missing exact IDs remain errors, not fabricated terminal states.

The workspace alert is a bounded, wrapping, full-width row above the split panes using existing surface/error tokens. Previously a terminal error occupied a flex column and squeezed the mobile catalog. This narrow correction does not change the 64px desktop rail, 320px catalog, mobile navigation or rename action bars. The previously reported mobile rename touch obstruction remains outside this stage.

## Local measurements and default

Apple M4 Pro, macOS arm64, 2026-09-12 local date. The one/two/four comparison used three fresh single-iteration subcases, serially run with no browser server active. These are small local fixtures, uncontrolled OS caches, not production NAS measurements. “Cold” means empty SQLite index, not cold filesystem cache. Setup/migrations are outside benchmark timers; allocated bytes are cumulative allocations, not retained memory.

| Fixture / median elapsed | 1 reader | 2 readers | 4 readers |
| --- | ---: | ---: | ---: |
| 10,000 flat movies, no sidecars, empty index | 528.311 ms | 497.355 ms | 481.617 ms |
| Same fixture, warm incremental index | 107.801 ms | 82.371 ms | 67.163 ms |
| 1,000 movies, valid ~64 KiB NFO each, empty index + hydration | 747.443 ms | 572.161 ms | 483.607 ms |

Raw samples/allocations: `readers-final.txt`. Four readers were fastest in these local samples. **Two** is a conservative default: it captures a substantial observed warm/parse improvement over one while limiting simultaneous file operations and parsed-record retention to half of four. This is not a claim that two is optimal on NAS. Valid-NFO cumulative allocation was about 585 MB per 1,000 imports across all settings; concurrency does not remove XML/metadata allocation cost.

## Review correction: preserve inspector work during automatic scans

Scan notifications no longer remount movie or TV inspectors. Each inspector serializes/coalesces read-only detail checks (15-second request deadline, abort on unmount). Availability is checked even while an edit or mutation is pending, but metadata/draft replacement is deferred until safe. Edit mode, changed draft values, saving, scraper/NFO dialogs, and movie rename operations block replacement; artwork/file workshops conservatively defer replacement while open, preserving their preview state. Clean detail updates do not toggle the loading branch or destroy child workshops. Discarding edits releases one coalesced refresh; failed saves retain their draft. Request/selection generations ignore obsolete responses.

A definitive HTTP 404, or a selected TV episode absent from a successful show response, marks the target missing without destroying unsaved input. A translated read-only alert disables new save, scrape, NFO, rename and artwork/file actions, including teleported apply dialogs. Transient/network/5xx failures are uncertainty, **not** evidence of deletion; writes remain disabled until a read-only Retry or subsequent scan verifies availability. Reappearance re-enables actions without overwriting a dirty draft. Clean missing targets clear their detail/actions. Already-issued mutations are not blindly aborted or duplicated; late responses cannot update another selection. Backend path/conflict validation remains authoritative. Explicit navigation/reload is not a new persistent draft store.

## Follow-up lifecycle and short-scan corrections

Same-show episode/season navigation now invalidates and queues availability checks for the **current selection**, including after a missing result. Old successful/failed responses cannot own the new selection's status. Checks remain serialized/coalesced; dirty show drafts survive navigation between units. TV mutations use operation-token-owned busy cleanup independent of selection generations: obsolete results cannot update a new unit, but settling an old request releases its busy state. Duplicate mutation events are rejected while an operation is pending. Mutation-triggered detail reads also reject obsolete selection generations.

Movie Save waits for independent availability checks after saving metadata, without waiting for draft replacement (which saving itself blocks). Once verified it continues through one NFO preview/apply. Missing/uncertain/timeout results explicitly report **metadata saved, NFO not written**, preserve input, and block new writes; unmount settles the waiting continuation without issuing NFO writes. This partial-result message is translated in English and Chinese.

A focused browser test exposed another tracking gap: an external scan completing in approximately 5 ms entirely between idle polls was present in history but never tracked as active, so no inspector/catalog refresh occurred. The follow-up records only the last **100-row recent scan ID/state/retry-count snapshot**, establishing a baseline on mount without replaying historical terminal jobs. Newly observed terminal scans after that baseline trigger one coalesced catalog/availability refresh even if their queued/running states were never observed. Duplicate snapshots do not replay notifications; older active jobs still complete through the existing active-page/exact-lookup mechanism, not a maximum-ID watermark. A burst that pushes an entirely unobserved short job outside the latest-100 window before polling remains outside this bounded history guarantee; no unbounded completion archive was added.

## First-load and same-state retry correction

Same-show episode/season navigation still rejects the obsolete initial response, but the current selection's availability check can populate the blank detail once loading settles. The existing dirty-draft, pending-operation and selection-generation guards remain unchanged.

Recent scan history compares both terminal **state and retry count** for each ID. A job retried externally back to the same `failed`, `cancelled` or `interrupted` state entirely between polls now triggers one catalog/inspector refresh. Duplicate state/retry pairs do not replay; the baseline remains at most 100 rows, with no bootstrap replay or ID watermark.

## Remaining measurement/safety limits

No production NAS/NFS/SMB tests, real-media throughput, cold-cache tests, syscall/lock traces, database lock-wait distribution, I/O-saturation latency, or production memory figures were collected. OS filesystem calls already in progress cannot necessarily be interrupted by context; bounded readers join them before returning. An accessible empty mountpoint remains indistinguishable from an intentionally empty source. Stat fingerprints still miss same-size/same-mtime replacements; full scans preserve saved metadata rather than force syncing NFO edits.
